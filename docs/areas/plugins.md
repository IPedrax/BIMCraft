# Плагины BIMCraft: папка, манифест, хост-ABI 1 и SDK

Плагин — это стороннее расширение, которое выполняется в песочнице WebAssembly и обращается к приложению
только через команды (`Session::execute`). Ядро о WASM не знает: у сессии есть динамический реестр внешних
команд (`engine::ExternalCommand`, `Session::register`), а всё остальное — чтение папки, проверка манифеста,
интерпретатор и лимиты — живёт в отдельном крейте `crates/plugin` (`bimcraft-plugin`). Гостевой SDK —
`crates/plugin-sdk` (`bimcraft-plugin-sdk`).

## Где лежат плагины

- `BIMCRAFT_PLUGINS` — папка плагинов. Пустое значение выключает плагины целиком.
- Иначе — подпапка `plugins` рядом с `favorites.json` в папке конфигурации пользователя:
  Linux `$XDG_CONFIG_HOME/bimcraft/plugins` или `~/.config/bimcraft/plugins`, Windows
  `%APPDATA%\BIMCraft\plugins`, macOS `~/Library/Application Support/BIMCraft/plugins`.
- Отсутствующая папка — это норма: плагинов нет, поведение приложения не меняется.
- Плагин — папка с `plugin.json` и модулем (по умолчанию `plugin.wasm`), либо одиночный `*.json`
  манифест в корне папки плагинов; путь к модулю в нём считается от папки манифеста.
- Один сломанный плагин не мешает остальным: он пропускается, причина попадает в журнал и в окно
  Manage > Plugins. Выключенные плагины и выданные им разрешения хранятся в `state.json` в папке
  плагинов (`disabled` и `permissions`); их команды не регистрируются, вкладка в ленте исчезает при
  следующем чтении папки. Файл старой версии `disabled.json` (`{"disabled": [...]}`) по-прежнему
  читается, если `state.json` ещё нет; первая же запись создаёт `state.json`, старое имя не удаляется.

## Манифест

Файл читается строго (`deny_unknown_fields`): лишний ключ, неизвестное разрешение, чужая версия ABI или
неверное имя — отказ при загрузке с указанием, что именно не так. Размер манифеста — до 1 МБ, модуля — до
16 МБ; функций — до 256.

```json
{
  "id": "rooms",
  "version": "0.1.0",
  "name": "Rooms",
  "description": "What the plugin is, for a person.",
  "abi": 1,
  "module": "rooms.wasm",
  "author": "BIMCraft",
  "license": "MIT OR Apache-2.0",
  "link": "https://example.org/rooms",
  "permissions": [],
  "functions": [
    {
      "id": "summary",
      "label": "Area Summary",
      "description": "What the function does, for agents.",
      "params": {"type": "object", "properties": {}},
      "tab": "Areas",
      "panel": "Rooms",
      "order": 1
    }
  ]
}
```

- `id` — до 64 символов, строчная латиница, цифры, `-`, `_`, `.`; `version` — латиница, цифры, `.`, `+`, `-`, `_`.
- `abi` обязан быть `1`. Другая версия — отказ с сообщением, для какой ABI собран плагин.
- `module` — относительный путь внутри папки плагина, без `..` и абсолютных путей.
- `permissions` — только `files` (см. ниже). Неизвестное разрешение — отказ. Это **заявка**, а не право:
право выдаёт человек в Manage > Plugins.
- `functions[].params` — JSON-схема параметров, как документация параметров команды; её строка попадает в
  каталог агентов.
- `tab`, `panel`, `label`, `order` — объявление ленты: вкладка принадлежит плагину, приложение её рисует.
  Без `tab` функция попадает в общий раздел «Plugins»; без `panel` — в панель с именем плагина. Подписи
  плагина — его данные и не переводятся.
- Команда плагина в сессии называется `plugin:<id плагина>:<id функции>`, например
  `plugin:<id плагина>:<id функции>`. Статическая команда с тем же id или алиасом не перекрывается: регистрация
  плагина будет отклонена.

## Хост-ABI версии 1

Модуль — обычный WASM с линейной памятью и обязательными экспортами:

| Экспорт | Подпись | Назначение |
|---|---|---|
| `memory` | память | входные JSON и ответы |
| `bimcraft_alloc` | `(i32 len) -> i32 ptr` | блок ровно `len` байт для хоста |
| `bimcraft_free` | `(i32 ptr, i32 len)` | необязательный: вернуть блок |
| `bimcraft_run` | `(i32 name_ptr, i32 name_len, i32 params_ptr, i32 params_len) -> i64` | вызов функции |

Ответ `bimcraft_run` упакован: старшие 32 бита — указатель, младшие 32 — длина JSON-ответа.

Хост предоставляет ровно три функции; всё остальное запрещено на этапе загрузки модуля (импорт WASI,
файлов, времени, случайных чисел — отказ «the module imports ...»):

| Импорт | Подпись | Назначение |
|---|---|---|
| `bimcraft.execute` | `(i32 ptr, i32 len) -> i64` | выполнить команду |
| `bimcraft.log` | `(i32 level, i32 ptr, i32 len)` | журнал: 0 info, 1 warning, 2 error |
| `bimcraft.info` | `() -> i64` | сведения о хосте |

`execute` принимает `{"command": "level", "params": {...}}` и возвращает конверт
`{"ok": true, "result": ...}` либо `{"ok": false, "error": "..."}`. Команда выполняется тем же
`Session::execute`: откат при ошибке, проверка всей модели и отказ в панике — бесплатно. Плагин может
вызывать команды BIMCraft, но не команды других плагинов.

`info` возвращает `{"app":"bimcraft","version":"0.10.0","abi":1,"units":"mm","project":"..."}`.

Ошибка обработчика в SDK приходит как `{"bimcraftError": "..."}`: хост превращает её в ошибку вызова,
транзакция откатывает всё, что успело измениться.

## Песочница и лимиты

|Что|Значение|
|---|---|
| Память гостя | 64 МБ (рост сверх — ошибка вызова) |
| Элементов в таблицах гостя | 16 384 во всех таблицах вместе (`table.grow` сверх — ошибка вызова) |
| Таблиц, экземпляров, памятей | 4, 8 и 1 на экземпляр модуля |
| Топливо на вызов | 20 000 000 (около секунды вычислений; бесконечный цикл останавливается) |
| Реальное время на вызов | 5 с (проверяется перед каждой командой и после вызова) |
| Команд на вызов | 1000 |
| Размер ответа | 16 МБ (столько же, сколько строка моста) |
| Модуль | 16 МБ |
| Манифест | 1 МБ |

Ловушка (trap), исчерпание топлива, превышение памяти, некорректный JSON или ответ не по формату — это
ошибка вызова с записью в журнал, а не падение приложения. Модуль исполняется без системных функций:
файлов, сети, часов и случайных чисел у гостя нет, потому что хост их не экспортирует.

### Где именно упал вызов

У wasmi нет трассировки стека, и ловушка или исчерпание топлива не говорят, на какой строке гостя это
случилось: сообщение было бы просто «all fuel consumed by WebAssembly». Поэтому каждый вызов помнит
последние шаги плагина — каждую команду с её параметрами, каждую строку журнала и `info` — вместе с
остатком топлива на момент шага:

- **ошибка вызова** (в строке состояния, в ответе CLI/MCP) получает хвост вида
  `; it stopped at ` + команда в обратных кавычках, если вызов остановила песочница (топливо, ловушка,
  память, реальное время), а не сам плагин;
- **журнал** получает строку вида
  `the call ran 24 command(s) and used 19.9 of 20.0 M fuel; the last steps, and the fuel left when each ran: ` + шаги
  с остатком топлива через запятую.

По ней видно, на что ушло топливо. Разбор ответа стоит примерно 0,7 тыс. топлива на байт, то есть
20 млн — это около 25 КБ ответов за вызов: полный `inspect` дома с библиотекой (около 19 КБ: типы,
семейства, материалы, типы проводов) съедает почти весь бюджет целиком. Поэтому `inspect {"brief": true}`
отдаёт уровни, счётчики, предупреждения, историю и размер библиотеки (`library`) без её содержимого —
четверть килобайта вместо девятнадцати, — и этого хватает сводке, которой не нужны сами типы. Правило
простое: команда, которая отвечает большим JSON, ограничивает плагин сильнее, чем кажется по лимиту
в 16 МБ на ответ.

## Разрешения

По умолчанию плагин читает модель (команды чтения) и меняет её командами; к диску он не прикасается.
Право `files` выдаётся **пользователем** в Manage > Plugins и хранится в `state.json` папки плагинов
(`"permissions": {"<id>": ["files"]}`). Манифест лишь заявляет его; без заявки выдать его нельзя, а
простое появление плагина в папке права не даёт — так же, как не даёт и первый запуск.

В окне плагина с заявкой показаны строка «File access», собственное описание плагина (зачем ему файлы)
и кнопки «Allow file access» / «Revoke file access»; состояние права видно рядом («Allowed» /
«Not allowed»). Отзыв действует сразу: следующие вызовы файловых команд отклоняются.

Какая команда трогает диск, говорит **метка в ядре**, а не список в плагине: у каждой команды в
`crates/core/src/commands.rs` есть поле `files` — `Read`, `Write`, `None`, либо `Conditional` для той,
что берёт путь только с некоторыми параметрами (`render` с `path`, `family` с `path`/`save`, `material` с
`texture.path`, `favorite` с любым действием, кроме `list`). Решение по параметрам принимает
`engine::touches_files`. В каталоге агентов у таких команд появляется поле `"files": "read"|"write"|
"conditional"`, а защитный тест `a_command_that_takes_a_path_is_marked_as_touching_files` падает, если у
команды появился параметр `path`, `save` или `texture.path`, а метки нет.

Без права такая команда отклоняется хостом **до** вызова `Session::execute`, с сообщением в журнал;
проверка идёт по настоящему id команды, поэтому алиас (`WA`, `SV`…) её не обходит. Так закрыты и
команды, которые раньше проскакивали: `schedule`, `export_crosscheck`, `export_fill_patterns`,
`import_fill_patterns`, `compare_crosscheck`. В версии 2 это же разрешение расширяется до хост-функций
чтения и записи данных; согласие на конкретные папки будет выдаваться пользователем отдельно.

## Undo и журнал

- Один вызов функции плагина — одна транзакция. Успешный вызов, изменивший модель, даёт **один** шаг
  истории с подписью `<Имя плагина>: <подпись функции>`; чтение шага не даёт.
- Ошибка в середине вызова (ловушка, ошибка команды, `bimcraftError`) откатывает модель, историю, фазу и
  путь сессии; новых шагов не остаётся.
- Журнал виден в окне Manage > Plugins и печатается в stderr CLI и MCP-сервера.

## CLI, MCP и агенты

Плагины читаются при старте `bimcraft-cli run`, `bimcraft-cli mcp` (собственная сессия сервера) и
десктопа (на отдельном потоке, не задерживая первый кадр). Команды плагинов попадают в каталог
`list_commands` с полем `"plugin"`:

```sh
# выполнить функцию плагина из папки plugins
BIMCRAFT_PLUGINS="$PWD/plugins" cargo run -q -p bimcraft-cli -- run --cmd 'plugin:rooms:summary'
```

MCP-инструмент `execute` принимает ту же команду, новых инструментов для плагинов нет. В режиме
`mcp --connect` каталог окна запрашивается по мосту (`{"op": "catalog"}`), поэтому агент видит и
плагины открытого окна. В сессии, которой разрешено только чтение (`mcp --read-only` или настройка окна
для агентов), команды плагинов подчиняются тому же режиму: чтение отвечает, изменение отклоняется и
откатывается.

## Окно плагинов и лента

Manage > Plugins: путь к папке, список загруженных плагинов (имя, версия, автор, число функций), статус
(загружен / выключен / ошибка с причиной), кнопки Enable/Disable, журнал с прокруткой и Refresh, который
перечитывает папку без перезапуска. Строки окна переведены через каталоги интерфейса; строки самих
плагинов — их данные и не переводятся.

Функции плагинов находятся и через Find (Ctrl+K), наравне с лентой и палитрой Tools: строка `«<подпись
функции> · <имя плагина>»`, Enter запускает её так же, как кнопка вкладки, а ответ с полем `report`
открывается в том же диалоге.

Каждый плагин объявляет свою вкладку в манифесте; вкладки плагинов идут после статических вкладок
BIMCraft, в порядке чтения плагинов, а функции без вкладки собираются в общий раздел «Plugins». Кнопка
первой версии запускает функцию без параметров: если параметры обязательны, ошибка показывается в строке
состояния. Выключенный плагин убирает свои команды и вкладку при следующем чтении папки.

Ответ функции, в котором есть строковое поле `report`, открывается в диалоге с заголовком в виде подписи
кнопки: текст плагина, по строке на строку моноширинным шрифтом, с Copy и Close. Это то, чем плагин
показывает человеку результат — отчёт о модели, список найденного и так далее; сам плагин интерфейса
рисовать не может. Без `report`, как и раньше, кнопка ничего не показывает: в CLI и MCP ответ команды
виден в любом случае.

## Как собрать плагин (SDK)

Плагин — отдельный `cdylib` со своим `[workspace]`, чтобы не входить в воркспейс BIMCraft. В папке
плагина его собирают и кладут рядом с `plugin.json`:

```sh
rustup target add wasm32-unknown-unknown
cargo build --target wasm32-unknown-unknown --release
cp target/wasm32-unknown-unknown/release/<имя крейта>.wasm plugin.wasm
```

Крейт:

```toml
[lib]
crate-type = ["cdylib"]

[dependencies]
bimcraft-plugin-sdk = { path = "путь/к/клонированному/BIMCraft/crates/plugin-sdk" }
serde_json = "1"
```

```rust
use bimcraft_plugin_sdk::{Value, execute, info_log};

fn summary(_: &Value) -> Result<Value, String> {
    let rooms = execute("elements", &serde_json::json!({"category": "room"}))?;
    info_log("counted the rooms");
    Ok(serde_json::json!({"rooms": rooms["count"]}))
}

bimcraft_plugin_sdk::export! { "summary" => summary }
```

`export!` объявляет функции, экспортирует `bimcraft_run`, `bimcraft_alloc` и `bimcraft_free`. В
`crates/plugin-sdk` есть единственный `unsafe` воркспейса: чтение указателей линейной памяти на границе
ABI гостя; в хосте, ядре и интерфейсе `unsafe` нет.

Публичного примера-плагина в репозитории нет: всё, что нужно автору, — манифест выше, `export!` и код
вызова команд. Сборка SDK проверяется в CI на тестовой фикстуре `crates/plugin/tests/sample-plugin`
(она читает площади помещений, пишет заметку одной командой и возвращает ошибку на проекте без
помещений); её модуль не хранится в репозитории, тест `crates/plugin/tests/sample.rs` запускает
собранный. Без сборки тесты пропускаются с командой сборки; в CI пропуск считается падением.

## Замеры

На машине разработки (Linux x86-64, release):

- release-бинарь `bimcraft-cli` — 33 121 456 байт; из них на символы `wasmi`/`wasmparser` приходится
  1 177 673 байта (≈1,15 МБ) — это и есть прирост от интерпретатора.
- модуль плагина — около 80 КБ (сборка `opt-level = "s"`, `lto`, `strip`).
- старт `bimcraft-cli commands` на 200 прогонах: 1,37 с без плагинов и 1,91 с одним плагином из 82 КБ,
  то есть около 2,7 мс на чтение, проверку и компиляцию одного плагина (кэш файлов прогрет).

Интерпретатор — `wasmi` 2.0.0 (MIT OR Apache-2.0), чистый Rust; зависимость не тянет C и системных
библиотек, поэтому собирается на всех целевых системах, включая riscv64 и Flatpak. Хост не держит
глобального состояния: плагины не влияют ни на модель, ни на скорость команд, когда их нет.

## Границы версии 1

Плагин объявляет ленту, но не рисует свой интерфейс; нет загрузки из интернета, маркетплейса, подписей и
обновлений; нет реактивных плагинов (события «после команды») до появления уведомлений об изменениях в
ROADMAP; нет хранилища данных плагина в файле проекта и нет сети. ABI v2 (защищённая доставка скриптов,
`net` и файловый посредник) — перспектива, точки расширения заложены: версия ABI в манифесте, разрешения,
журнал и проверка в хосте.
